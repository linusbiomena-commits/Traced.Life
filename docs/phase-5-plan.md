# TRACED Platform: Phase 5 Implementation Plan (Authorized Admin Portal)

Status: **APPROVED (26 Nov 2026) and IMPLEMENTED** with the owner's reduced scope; see `docs/phase-5-report.md` for what was built. The text below is the original plan, kept for reference. Written 26 November 2026 on top of Phase 4 (`2debbf1`).

## 0. Principles
- Reuse the Phase 1 authentication system, sessions, MFA, CSRF, rate limits, audit service and the existing permission catalogue (`server/migrations/0003`, `server/src/modules/rbac/catalogue.ts`). **Add no new authentication system and no new roles.**
- Every admin endpoint uses `requirePermission(...)` (which already enforces MFA for privileged roles), returns `no-store`, and writes an audit event for every read of personal data and for every change.
- Responses are built by explicit per-endpoint allowlists, the same as the staff API. Endpoints that don't need personal data (stats, staff lists, email monitor, audit viewer) never return it.
- Use real database queries only. No fictional figures.
- Additive migrations only (`0008_…` onward). Existing public pages stay untouched; `check:portal` must keep passing.
- Bilingual EN/AR + RTL, desktop-first but usable at 375 px. Admin pages live under `/traced/admin/` (and `/ar/traced/admin/`), generated by `build-portal-pages.mjs` like the staff pages.

## 1. Pre-work (small, security)
1. **Trusted proxy hardening.** `server/src/middleware/request.ts` takes the *leftmost* `X-Forwarded-For` entry when `TRUST_PROXY=true`. A client can forge that entry, which would let it dodge IP rate limits and the sign-up limiter behind Cloud Run or Vercel. Change it to take the entry that is `TRUST_PROXY_HOPS` positions from the right (default 1), test spoofed headers, and keep the E2E harness working. This is not exploitable today because nothing is deployed, but it must be fixed before Phase 8.
2. Add a short "admin privacy matrix" test helper (a canary sweep like the staff one) so every new endpoint is covered as it's built.

## 2. Workstreams

### 2.1 Admin authentication and shell
- Admin sign-in page (`/traced/admin/sign-in/`), reusing `/auth/sign-in`, with mandatory MFA enrolment and challenge for `admin`, `super_admin`, `auditor` and `lab_operator` (already `requires_mfa`). Recovery codes, password reset and the invite acceptance page already exist (accept-invite was built in Phase 4).
- Role-aware navigation: menu items appear only for permissions the user holds. The server re-checks every request regardless.
- Routing: privileged users who sign in on the customer or staff page are sent to the admin portal; customers and staff get "No access" on admin pages and 403 from the API.
- Session rules unchanged (12 h, 30-minute idle).

### 2.2 Dashboard (`stats.read`)
`GET /admin/stats`: total customers, total registrations, awaiting collection, samples collected, collections today and this month (Asia/Riyadh), per-branch collections, active staff, failed emails, status distribution. Recent activity shows audit events **without personal data** (event type, actor role, resource type, time). Aggregates only, so auditors can use it.

### 2.3 Customer and patient management (`registration.read_full`, `registration.manage`)
- `GET /admin/registrations` with search (tracking ID exact, email, mobile, patient name), filters (status, branch, date range, QR status) and keyset pagination. The list shows minimal fields; searching by personal data is audited (search terms stored hashed or redacted, never raw).
- `GET /admin/registrations/:id`: full detail (patient names, DOB, age, gender, relationship/guardian, account holder, verified email, mobile, consents with versions, tracking ID, QR status and lifecycle, sample/collection record, status history, patient revision history). **Each view writes a `registration.viewed_full` audit event.** Encrypted revision history is decrypted only here.
- `GET /admin/customers` and `/admin/customers/:id`: account plus their registrations.
- Changes (`registration.manage`): cancel a registration (reason required; QR revoked; tracking ID never reused); change the collection branch before collection (covers decision §16.4 of the Phase 4 report if approved); admin correction of patient data before collection (keeps revision history, invalidates identity verification, as for customer corrections). After collection there are no silent edits; corrections become Phase 6 custody correction events.

### 2.4 QR management (`qr.revoke`)
UI for the existing `POST /admin/registrations/:id/qr/revoke` (reason required, optional regenerate and notify), plus `GET …/qr/history` (lifecycle with actor, role, reason and time; never tokens) and "resend QR email". The original tracking ID is always kept.

### 2.5 Staff management (`staff.manage`; admin roles need `admin.manage`)
- List and detail with status, roles, branches, last sign-in and recent activity (from audit).
- Invite by email (reuses the existing invitation tokens and email templates), assign roles: `admin` may assign `collection_staff` and `lab_operator` only, and only `super_admin` may assign `admin`, `super_admin` or `auditor`.
- Activate, suspend and deactivate (revokes sessions immediately); assign and remove branches (`staff_branch_assignments` with `revoked_at`, already present).
- **Guards:** no self-elevation; can't change your own roles or suspend yourself; the last active `super_admin` can't be suspended, deactivated or demoted (checked inside a transaction with a row lock). Every change is audited with before/after values.

### 2.6 Branch management (`branch.manage`)
Create, edit (EN/AR name, city, code, address), activate and deactivate `collection_branches`. Deactivation keeps history, blocks new registrations and collections there, and warns when registrations are still awaiting collection. Shows staff assignments and per-branch statistics.

### 2.7 Collection instructions (`form.approve` / `consent.manage`; to confirm in §4)
Migration 0008 adds a `draft` status (and `approved_by`/`approved_at`) to `collection_instructions`, keeping published versions immutable (the existing trigger). Flow: create draft (EN+AR text, checklist) → edit draft → approve/publish (super admin; records approver) → older version retired. Version history is viewable. The UI clearly labels provisional versions; **production still refuses provisional content**. The same pattern is optionally applied to `consent_documents` (read-only history view in Phase 5; publishing stays with `consent.manage`).

### 2.8 Email monitoring (`email.manage`)
List `email_outbox` (template, status, attempts, next retry, provider message ID, timestamps, recipient masked as `f***@d***.com`); filter by status and template; "retry now" for failed messages (audited, rate limited). The body, tokens and links are never returned.

### 2.9 Audit log viewer (`audit.read`)
Extend the existing `GET /admin/audit-logs` with date, event type, actor, resource and outcome filters and keyset pagination. Read-only, with no edit or delete paths. Auditors see redacted metadata (no personal data); a "verify chain" action runs the existing hash-chain check and reports the result.

### 2.10 Reports and exports (`report.export`, `report.export_pii`)
- Operational CSV (no personal data): registrations by status, branch and month; collections by branch and day; email delivery summary.
- PII CSV (`report.export_pii`, super admin only): registration list with contact details. Requires re-entering MFA (step-up), a reason, and a date range limit.
- All exports are audited (who, filters, row count) and protected against formula injection (prefix `'` for values starting with `= + - @ \t \r`), UTF-8 with BOM for Arabic in Excel.

## 3. Database (migration 0008, additive)
- `collection_instructions`: allow `draft`; add `approved_by`, `approved_at`.
- Indexes for admin search and pagination (registrations by status/branch/created_at; outbox by status/next_attempt_at; audit_logs by created_at/event_type/actor).
- `users`: `suspended_at`, `deactivated_at`, `status_reason` if not already covered by `users.status` (to verify).
- Optional `admin_saved_filters`: **not planned** (avoid scope creep).
- No changes to applied migrations 0001–0007.

## 4. Decisions needed before or during Phase 5
1. **Branch transfer:** allow admins to change a registration's collection branch before collection? (Recommended: yes, audited.)
2. **Who approves collection instructions:** `form.approve` (super admin) as proposed, or a new lab-approval role? (Recommended: super admin now; add a role only if the lab needs its own login.)
3. **PII export:** keep super-admin only (current catalogue) with step-up MFA? (Recommended: yes.)
4. **Admin search by personal data** (name, email, phone): allowed for `registration.read_full` holders, audited? (Recommended: yes.)
5. **Customer account actions by admins** (resend verification, lock/unlock, deactivate): include in Phase 5? (Recommended: lock/unlock and resend only.)

## 5. Testing plan
- Unit and integration tests (Vitest, real PostgreSQL) per endpoint: permission matrix for all six roles (positive and negative), MFA enforcement, object-level checks, audit events written, allowlist key-set assertions, canary sweep for auditor and stats endpoints, last-super-admin lock-out guard under concurrency, privilege-escalation attempts, CSV injection cases, pagination stability.
- Browser tests (Playwright, Edge): admin sign-in with MFA, dashboard, registration search and detail, QR revoke with reason, staff invite → accept → assign branch → suspend, branch deactivate, instruction draft → publish, email retry, audit filter, export; Arabic RTL; 375 px.
- Regression: all 154 existing tests and 16 browser tests keep passing; `check:portal` passes; no existing public page modified.
- Screenshots in `docs/phase-5/screenshots/`; report in `docs/phase-5-report.md`.
